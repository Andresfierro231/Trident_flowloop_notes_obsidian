
## The model in one picture

TRIDENT represents a loop as **short pipe cells**. Each cell can have a fluid temperature, a pipe temperature, and an insulation temperature. Heat enters through the heater, moves between those layers and along the loop, and leaves through the room or cooler. The solver finds temperatures for which every cell’s incoming and outgoing heat balance.

```
flowchart LR
    A["Facility geometry, materials, heater and cooler inputs"] --> B["Divide loop into cells"]
    B --> C["Build heat-transfer connections"]
    C --> D["Solve cell energy balances"]
    D --> E["Temperatures, flow and heat ledgers"]
    E --> F["Compare with qualified sensor observations"]
```

## The four physical-model stages

| Stage | Question it answers | What it adds |
|---|---|---|
| **M0** | Can the heat-transfer pieces balance? | A small radial network, with no circulating fluid |
| **M1** | What is the temperature distribution in a stagnant segmented loop? | Fluid, pipe, and optional insulation cells; radial transfer and axial fluid/pipe conduction |
| **M2** | What if the loop flow rate is supplied? | Signed flow carries fluid enthalpy between cells |
| **M3** | What flow rate would buoyancy and hydraulic resistance permit? | Repeated M2 thermal solves coupled to a loop momentum balance |

For each temperature node, the core steady equation is:

heater input+heat received from neighbors -heat sent to neighbors and surroundings=0.

An internal connection removes heat from one node and gives **the same amount** to the other. That is why the heat ledger is central: it lets us inspect where the energy went. M2 adds flow transport; M3 finds flow values for which buoyancy drive equals friction and local losses. The M2 equation note (andrew\_WorkSpace/trident\_modeling\_initiative/docs/theory/M2\_PRESCRIBED\_FLOW\_ENERGY.md) and M3 equation note (andrew\_WorkSpace/trident\_modeling\_initiative/docs/theory/M3\_NATURAL\_CIRCULATION\_MOMENTUM.md) are good next reads.

There is also a **separate reduced-zone model** for effective regional temperatures and relaxation behavior. Its regions are empirical energy states; they should not automatically be called fluid, pipe, or insulation temperatures. See its implementation (andrew\_WorkSpace/trident\_modeling\_initiative/src/trident\_thermal/network/reduced\_zone.py).

## Try an actual run

From the modeling repository directory, run this synthetic five-cell M1 example with a **new** output path:

```
PYTHONPATH=src python3.11 -B -m trident_thermal.solvers.m1 \
  config/examples/m1/pipe_axial_diagnostic.yaml \
  /tmp/my_first_trident_m1_run
```

The input is andrew\_WorkSpace/trident\_modeling\_initiative/config/examples/m1/pipe\_axial\_diagnostic.yaml. The resulting directory contains:

- `resolved_config.yaml` — the inputs after defaults are resolved.
- `model_form_property_summary.json` — which physics, properties, and numerical method were selected.
- `result.json` — temperatures, convergence information, and heat contributions.

I ran that example to verify the interface. It converged with 10 W heater input and approximately −10 W external heat transfer; global energy closure was about −4.7×10⁻¹¹ W. Its temperatures are **synthetic test results**, not ACU measurements. In `result.json`, start with `converged`, `temperatures_K`, `free_residual_inf_W`, `global_energy_closure_W`, and `heat_contributions`. The signed `heat_by_kind_W` totals are whole-network sums, so internal transfers cancel there; use `heat_contributions` to see individual transfers.

For code use, the M1 solver (andrew\_WorkSpace/trident\_modeling\_initiative/src/trident\_thermal/solvers/m1.py) exposes `load_m1_problem`, `solve_m1`, and `run_m1`. M2 and M3 have analogous command-line modules. M3 can report **multiple candidate flow roots** and declines to select one when the scan does not establish a unique root.

## How I would explain it to a colleague

> “We divide the TRIDENT loop into axial cells and solve a heat balance for fluid, pipe, and sometimes insulation temperatures in each cell. Heater, ambient loss, and cooler behavior are explicit inputs. We can hold flow at zero, prescribe it, or calculate candidate natural-circulation flow from buoyancy and hydraulic losses. Every run records its selected model form, resolved inputs, temperature results, and conservation ledger. Right now the ACU and VCU geometry and measurement mappings have different evidence status, so the working examples are diagnostic models rather than validated facility predictions.”

The most productive questions to ask together are: **Which facility and geometry revision? Which flow mode and cooler form? Which inputs are measured versus assumed? Does energy close? Which sensor is being compared to which model state?** For the current VCU data, timed power/water conditions and the installed sensor mapping still need to be tied to candidate steady windows before fitting. Current status (andrew\_WorkSpace/trident\_modeling\_initiative/STATUS.md) tracks those gates.
